# 홈페이지2(데스크톱) — 서비스 성격에 맞게 수정하기 위한 검토 리스트

> 이 문서는 `prototype/홈페이지2(데스크톱)/index.html` 시안을 frontend-v2에 적용하기 전에
> 반드시 결정해야 할 사항을 정리한 검토 문서다. 최종 선택은 개발자 승인 후 확정한다.
>
> 참조 문서: `specs/home.md`, `design-decisions.md`, `component-design.md`, `src/types/concert.ts`

---

## 0. 전제: 프로토타입과 현재 서비스의 성격이 다르다

| | 홈페이지2 프로토타입 | 현재 서비스 (frontend-v2) |
|---|---|---|
| 정체성 | **예매·비교 포털** (OTA 스타일) | **연주 프로그램 검색 아카이브** (OPUS INDEX) |
| 핵심 가치 | 공연을 "산다" — 가격 비교, 할인, 랭킹, 예매 | 공연의 프로그램(작곡가·곡명)으로 공연을 "찾는다" |
| 데이터 | 실데이터 없는 시안 (하드코딩) | KOPIS 기반 + AI 프로그램 추출, 향후 3개월 한정 |
| 거래 | 티켓 판매 전제 | 티켓 판매 없음 → 예매처 외부 링크 제공 (specs card-015/016) |
| 계정 | 로그인/마이페이지 있음 | 유저 시스템 없음 |

**기본 원칙**: 디자인의 *톤과 레이아웃*은 가져가되, *기능*은 현재 데이터 모델과
specs 정책이 지원하는 것만 넣는다. "있어 보이는 가짜 데이터"는 넣지 않는다.

## 1. 데이터가 없는 기능 — 뺄지, 조건부로 넣을지 결정

프로토타입의 요소를 현재 데이터 모델(`src/types/concert.ts`)과 대조한 결과:

| # | 프로토타입 요소 | 필요한 데이터 | 현재 상태 | 검토 방향 |
|---|---|---|---|---|
| 1 | 지역 필터 + "지역별 공연" 섹션 | 정규화된 지역 필드 | `venueAddress`(문자열)만 있음 | 주소 파싱으로 파생 가능하나 **백엔드 선결제**. 1단계에선 제외 검토 |
| 2 | 카테고리 섹션 (교향곡/오페라/발레…) | 장르/카테고리 필드 | 없음. `programs`(작곡가·곡명)만 있음 | KOPIS에 장르 정보가 있는지 확인 필요. 없으면 버림 |
| 3 | 할인 표기 (취소선 가격, "15%") + 할인 배너 | 할인율/원가 데이터 | `seatPrices`, `minPrice/maxPrice`만 있음 | 버림. 배너는 "다가오는 공연 안내" 등으로 용도 교체 검토 |
| 4 | 배지: 매진임박/신규오픈/단독판매/단 3회 | 판매 상태 데이터 | 없음 | **common-001 위반** — 상태 배지는 '공연중/공연예정' 2종만. 기존 `ConcertStatusBadge`로 대체 |
| 5 | 좋아요(찜) 버튼 | 유저 시스템 | 로그인 자체가 없음 | 버림 (비로그인 로컬 찜은 과설계 — YAGNI) |
| 6 | 예매 랭킹 (주간 TOP 5, ▲▼ 순위변동) | 예매/판매 데이터 | 우리는 티켓을 안 팔아서 원천 데이터가 없음 | 버림. 대체 안: "곧 시작하는 공연"(status+기간 기반) 섹션 |
| 7 | 티켓 오픈 예정 + 알림신청 버튼 | 오픈 일정 + 알림 인프라 | 둘 다 없음 | 버림 (백엔드+푸시 인프라 필요) |
| 8 | 인기 검색어 칩 | 검색어 집계 | PostHog로 `search` 이벤트 수집 중 | **2단계 가능**. 초기엔 데이터 충분할 때까지 고정 예시 검색어(NoResult의 예시와 공유) |
| 9 | 히어로 탭: 아티스트/공연장/앙코르 상영 | 전용 페이지 + 데이터 | 없음 (현재 홈+상세만) | 버림. 탭 자체를 빼거나 "공연 검색" 단일 유지 |
| 10 | GNB 메뉴: 특가/할인, 매거진 등 | 전용 페이지 | 없음 | 실제 존재하는 화면만 노출 (현재 SiteHeader 구조 유지) |
| 11 | 로그인/마이페이지/공연 등록 문의 | 유저 시스템, 제휴 채널 | 없음. KOPIS 기반이라 공연 등록도 받지 않음 | 버림. topbar 자체를 뺄지 결정 |

> 판단 기준(공통): **"이 데이터가 DB에 실제로 존재하는가?"** 가 아니면 UI에 넣지 않는다.
> 존재하지 않는 기능 UI는 사용자 기대만 만들고 신뢰를 깬다.

## 2. specs 정책과 충돌하는 부분

프로토타입을 그대로 옮기면 specs 정책을 깨는 지점들:

- [ ] **search-009 (검색 버튼 커밋)**: 프로토타입 검색 패널은 필드가 즉시검색처럼 보인다.
  패널 형태를 채택하더라도 "검색" 버튼을 눌러야 결과가 바뀌는 흐름을 유지할 것.
- [ ] **search-001 (placeholder는 실제 가능한 검색어만)**: "조성진, 라 보엠" 같은 예시가
  실제 데이터에 존재하는지 확인. 현재 `SearchBar`의 placeholder와 통일.
- [ ] **search-003 (정렬 3종)**: 프로토타입 홈엔 정렬 UI가 없다. 결과 목록 진입 후 기존
  `SortSelect`(공연임박순/낮은가격순/높은가격순)를 유지하는지, 홈에 녹여낼지 결정.
- [ ] **search-004 (상태 탭 + 건수)**: 전체/공연중/공연예정 탭(+괄호 건수)을 어디에 둘지.
  프로토타입의 탭(공연검색/아티스트/…)은 성격이 다르므로 혼동하지 말 것.
- [ ] **common-001**: 상태 배지 2종 제한 (위 1-4 참조).
- [ ] **card-003~019 (카드 정보 표기 규칙)**: 프로토타입 카드는 규칙이 요구하는 정보가
  대부분 빠져 있다. 재구성 필수 — 아래 3절 참조.
- [ ] **card-013/014 (가격 표기)**: '전석 무료' / '가격 정보가 제공되지 않습니다' /
  좌석별 가격 규칙. 할인 표기를 버리더라도 이 규칙은 그대로 적용.
- [ ] **card-015/016 (예매처 링크)**: '<예매처> 공식 티켓 예매' UI와 바로가기는
  우리 서비스의 "구매 대신 연결"이라는 핵심 행동. 프로토타입 카드에 없음 → 반드시 포함.
- [ ] **head-001 (헤더에 탐색 가능 기간 표시)**: 프로토타입 헤더에 없음. 스타일만 바꾸고
  기능은 유지할 것.
- [ ] **exception-03 (no-result)**: 홈 톤을 바꾸면 `no-result` 프로토타입·구현과의 톤
  정합성도 함께 갱신할 것 (부분 적용으로 페이지 간 단절 방지).
- [ ] **feedback-001/002**: '서비스 의견 보내기' 플로우가 새 헤더/푸터에 그대로 존재하는지 확인.

## 3. 카드 디자인 — 우리의 핵심 차별점이 빠져 있음

프로토타입 카드 = 포스터 + 제목 + 날짜 + 가격.
우리 서비스의 존재 이유 = **프로그램(작곡가 - 곡명)**.

앨범형 카드(`ConcertCardAlbum`)를 프로토타입 톤으로 다시 그릴 때:

- [ ] 프로그램 영역 (작곡가 - 곡명, `… 외 N곡`) 유지 — card-008/018
- [ ] hover 시 전체 프로그램 flyout 유지 — card-010, view-004
- [ ] 검색어와 일치하는 곡을 프로그램 영역에 메인 표시 유지 — search-008
- [ ] 아티스트 라벨/이름 한 줄 배치 규칙 유지 — card-005/011
- [ ] 장소 2줄(홀 이름 + 상세 주소), 날짜+요일·시간, 러닝타임/연령/장소 누락 시 `-` 유지
      — card-003/004/012
- [ ] '<예매처> 공식 티켓 예매' 버튼 포함 — card-015/016
- [ ] **포스터 null fallback으로 프로토타입 채택 가치 높음**: `poster: string | null` 이므로
      포스터가 없는 공연에 프로토타입의 "뮤트 그라데이션 + 라인 아이콘" 플레이스홀더가
      실제로 유용. 공식 fallback 스펙으로 채택 제안.
- [ ] 프로토타입의 카드 hover `translateY(-6px)` + 그림자 강조 패턴: 현재 리스트형 카드에는
      적용 부적합(행 구조), 앨범형에만 적용 검토.

## 4. 레이아웃 / 정보구조

- [x] **홈의 정체** — ✅ 확정 (2026.10.23): **도구형(검색 우선) 유지**.
      메인 섹션은 인기 공연 등 큐레이션 섹션 없이 기존처럼 공연 목록을 바로 보여주고,
      프로토타입은 톤(색·폰트·검색 패널 카드형 디자인·포스터 플레이스홀더)만 적용한다.
      근거: ① 서비스 정체성(프로그램 검색 아카이브)상 공연 카드 목록이 곧 콘텐츠,
      ② 3개월 한정 데이터 규모에서 큐레이션 섹션 다수는 "비어 보이는" 위험,
      ③ 검색 게이트 방안(홈=검색만)은 라우팅/상태 분리 비용 대비 이득이 없고
      둘러보기 경험을 차단함.
- [ ] 프로토타입 검색 패널은 4필드(공연명·연주자/지역/관람일/인원·좌석)지만 우리는
      **검색어 1개**만 지원. '관람일'은 기존 기간 선택 UI(별도 프로토타입 존재)로, '인원·좌석'은
      제거. 패널을 2~3필드로 재구성할지, 기존 2단 구조(히어로+검색바 / 상태+기간 바)를
      유지하며 스타일만 적용할지 결정.
- [ ] 큐레이션 섹션(인기/곧 시작하는 공연 등)을 넣으면 **각 섹션마다 별도 API와
      queryKey, staleTime 설계**가 필요하다 — design-decisions §4~5 참조.
      "이 섹션은 무한정 늘어나는 목록인가, 유한한 소수인가"에 따라 페이지네이션 여부도 결정.
- [ ] 섹션의 "전체보기" 링크는 **URL 파라미터가 세팅된 상태로 연결** (URL = SSOT 원칙,
      view-002 패턴). 예: 지역 서울 섹션 → `?region=seoul` 검색 결과.
- [ ] 프로모션 배너를 유지한다면 용도를 실제 있는 것으로 교체 (예: "향후 3개월 탐색
      가능 기간 안내" — head-001과 연동).

## 5. 디자인 시스템 / 토큰

- [ ] **색상**: 프로토타입 `--navy/--gold/--ivory` vs 현재 M3 계열 토큰
      (`primary/surface-container/outline-variant`…). 새 팔레트로 갈아탈지,
      기존 토큰에 accent(gold)를 추가로 얹을지 결정.
      - 프로토타입의 "버튼 hover 시 gold 배경 + 남색 글자" 패턴은 대비비(접근성)와
        토큰 일관성 측면에서 재검토 권장. gold는 강조(배지·숫자·언더라인)로 제한 제안.
- [ ] **폰트**: 현재 `next/font`로 Playfair Display + Hanken Grotesk 사용 중.
      프로토타입은 Pretendard + Noto Serif KR(한글 세리프) — 한글 헤드라인에 세리프를 쓰려면
      `next/font`로 Noto Serif KR 추가 검토. `<link>` 태그 직접 삽입 방식은
      Material Symbols 예외 외에는 지양 (layout.tsx 관행 유지).
- [ ] **아이콘**: 현재 Material Symbols 아이콘 폰트(`Icon.tsx`). 프로토타입은 커스텀 라인
      SVG 스프라이트(바이올린/피아노/오페라 등 악기·예술 아이콘) — Material Symbols에 없는
      종류다. 커스텀 SVG 세트를 도입할지(Icon 컴포넌트 확장), 존재하는 근사 아이콘으로
      대체할지 결정. 카테고리/플레이스홀더를 채택하면 필요.
- [ ] **기존 화면과의 톤 통일**: 홈만 새 톤이 되면 안 된다. 함께 갱신 대상 —
      no-result, not-found, 기간 선택 UI, 전체 프로그램 UI, 오류 제보 모달/바텀시트,
      SiteHeader/SiteFooter, 검색결과 리스트형/앨범형 전체.

## 6. 기술 아키텍처 고려사항

- [ ] **새로운 URL state**(지역, 카테고리 등)를 추가하면 전부 nuqs 파서로 정규화
      (exception-02 패턴: 잘못된 값 → 기본값 clamp).
- [ ] 실제 포스터 이미지가 들어오면 `next/image` 최적화 + 고정 aspect-ratio로 CLS 방지.
      프로토타입은 포스터가 없어 이미지 로딩 이슈가 검증되지 않았다.
- [ ] **SEO**: 포털형 홈(카테고리·지역 랜딩)은 SEO 가치가 커진다. 현재 CSR 우선 전략
      (design-decisions §8)에서 "서버 prefetch + HydrationBoundary"로 확장할 트리거인지 판단.
- [ ] **접근성**: hover 전용 flyout(card-010/view-004)에 키보드 포커스/터치 대응,
      gold 텍스트 대비비(WCAG AA), 아이콘 버튼(좋아요 등)에 `aria-label`.
- [ ] **성능**: 히어로의 다중 radial-gradient + `backdrop-filter: blur`는 저사양 기기에서
      비용이 있다. 실측 후 유지 결정.
- [ ] **모바일**: 이 시안은 데스크톱 전용이다. 프로토타입 안의 반응형 CSS는 참고용일 뿐 —
      모바일 별도 시안(`홈페이지(모바일)` 계열 관행처럼)을 만들지, 데스크톱 시안을
      축소 적용할지 결정 필요. specs의 모바일 전용 규칙(view-003, card-002/006/009) 충족 여부 확인.

## 7. 적용 우선순위 제안 (승인 필요)

| 단계 | 내용 | 전제 조건 |
|---|---|---|
| **1단계 — 톤 적용** (데이터·정책 변경 없음) | 색/폰트/헤더·푸터 스타일, 히어로+검색 리디자인, 포스터 null 플레이스홀더, 고정 예시 검색어 칩 | 없음 — 기존 API 그대로 |
| **2단계 — 파생 데이터** | 지역 필터(주소 파싱), "곧 시작하는 공연" 섹션(기존 API 재사용), 인기 검색어(PostHog 집계) | 백엔드 경량 작업 |
| **3단계 — 신규 기능** | 장르 카테고리(KOPIS 데이터 확인), 알림, 찜, 인기 검색어 실시간 집계 | 백엔드/인프라 신규 개발 |
